# Demo: one real walkthrough of the human-gated pipeline

`solution/state/` and `stubs/outbox/*.jsonl` are gitignored (they're run-specific
output, regenerated by `py -m solution review` / `apply`), so this folder is a
small, hand-picked, **real** excerpt -- not synthetic -- showing the pipeline
end to end on the actual 140-transcript corpus. Every snippet below is verbatim
output from a real run; nothing here was hand-written to look good.

## How this was produced

```
py -m solution review                 # -> solution/state/review_queue.md (183 items)
#   ... a human edits solution/state/review_decisions.json: pending -> approved/rejected ...
py -m solution apply                  # -> stubs/outbox/jira.jsonl, stubs/outbox/slack.jsonl
```

Out of 183 items queued for review across the full corpus, 4 were decided here
to illustrate all three outcomes a reviewer can choose:

| key | action | decision | why |
|---|---|---|---|
| `call-051#9#bug` | file-new (P1) | **approved** | Clean, high-confidence, self-contained SSO outage report. |
| `call-004#23#bug` | corroborate -> `PROJ-101` | **approved** | Same symptom (timezone-shifted timestamps) as an already-tracked bug; attach, don't refile. |
| `call-011#41#bug` | file-new (P3) | **approved** | Concrete, well-evidenced apostrophe-in-name link-truncation bug (31 affected members, confirmed pattern). |
| `call-011#33#bug` | file-new-low (P3) | **rejected** | See "A real judge limitation, caught by the gate" below. |

See [`review_queue_excerpt.md`](review_queue_excerpt.md) for these 4 items in
the same format a reviewer actually sees them in, and
[`review_decisions_excerpt.json`](review_decisions_excerpt.json) for the
decisions with the reviewer's reasoning attached to each.

## What came out the other side

[`jira_outbox_excerpt.jsonl`](jira_outbox_excerpt.jsonl): 2 tickets filed
(`PROJ-1001` for call-011's apostrophe bug, `PROJ-1002` for call-051's SSO
outage) -- both include the account, the verbatim transcript evidence, the
turn span, and the judge's own rationale string, so an engineer reading the
ticket can see exactly why the system thought this was worth filing.

[`slack_outbox_excerpt.jsonl`](slack_outbox_excerpt.jsonl): 3 messages -- one
per filed ticket, plus one for the corroboration, which explicitly says *"No
new ticket filed -- added as a corroborating source on PROJ-101"* rather than
silently doing nothing, so the channel has a record of why call-004 didn't
produce a fourth ticket.

Nothing was filed or posted for `call-011#33#bug` -- it was rejected before
`apply` ever ran, so it never reached the stubs.

## A real judge limitation, caught by the gate

`call-011#33#bug` and `call-011#41#bug` are actually **the same underlying
issue**. Sofia (the customer) says "okay -- the actual bug" at turn 33, then
pauses for a beat, then delivers the real, technical apostrophe/404 report at
turn 41. That's an 8-turn gap -- one turn past `heuristic_judge.py`'s
clustering merge threshold -- so the rule-based judge produces two candidates
instead of one: a near-empty "signpost" candidate and the real report.

This was found while building [`solution/eval/run_eval.py`](../eval/run_eval.py)
against the labeled dev set (see that module's commit history) and is
documented, not silently patched around: a global widening of the clustering
gap was tried, measured against the eval, and reverted because it caused a
*worse* false positive elsewhere (merging call-010's distinct Azure AD bug into
an unrelated tracked Okta issue, `PROJ-064`). It's left as a known limitation of
the deterministic heuristic judge -- and this demo shows the human-review gate
doing exactly what it's there for: a person clears the low-content duplicate
in about five seconds without a wrong ticket ever reaching Jira. See
WRITEUP.md for the full discussion of what the eval catches versus what a
reviewer still has to catch by hand.
